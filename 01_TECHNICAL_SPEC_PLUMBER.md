# MiniGames / «Водопроводчик» — итоговое техническое задание

**Версия ТЗ:** 1.1 (AssetGen + обязательные примитивные fallback-спрайты)  
**Статус:** утверждено по результатам 69 решений заказчика  
**Адресат:** OpenCode, разрабатывающий в существующем проекте MiniGames  
**Обязательные сопроводительные документы:** `02_OPENCODE_EXECUTION_RULES.md`, `03_ASSETGEN_AGENT_SPEC.md`, `.opencode/skills/minigames-assetgen/SKILL.md`  
**Приоритет:** сохранение существующей MiniGames и игры «Переливашки», корректность игровой модели, воспроизводимость уровней, качество пользовательского опыта, доказуемая приёмка.

> Это ТЗ — полный объём обязательной реализации, а не перечень идей «на потом». Работа выполняется поэтапно, но считается завершённой лишь после выполнения применимых требований и приёмочных проверок. Отдельно оговорённая **будущая монетизация** не разрабатывается сейчас. Уже существующие механизмы MiniGames следует переиспользовать, а не дублировать. Сопроводительный регламент устанавливает порядок самостоятельной работы и обязательные точки остановки.

## 1. Цель и границы продукта

Создать вторую игру платформы MiniGames — браузерную PWA-головоломку на Phaser, рабочее название **«Водопроводчик» / Pipe Connect**. Основное действие: пользователь собирает систему труб, **сам запускает воду**, наблюдает дискретную симуляцию заполнения, устраняет ошибки и доставляет заданные жидкости до получателей. Возможности усложняются постепенно: новые формы труб, несколько источников и целей, препятствия, клапаны, разветвления, смешивание цветов, точное дозирование и визуальное программирование подачи. Генерация уровней бесконечная, с проверяемой решаемостью и адаптацией сложности.

Целевая аудитория — в том числе дошкольники, не умеющие читать, а также взрослые. Игровое обучение опирается на действие, подсветку, жесты и визуальную демонстрацию, а не на текст. Платформа общая с «Переливашками»: единая PWA, SDK игровых модулей, учётная запись, прогресс, сервер, офлайн-работа и настройки.

### 1.1 Обязательные продуктовые принципы

1. **Интересна сама головоломка:** победа основана исключительно на реально вычисленных условиях, без скриптового «автовыигрыша».
2. **Нет непреодолимых тупиков:** подсказки, решение, пропуск и адаптация сложности предусмотрены, но ненавязчивы.
3. **Действительно красивая жидкость:** не одноцветная линия, не дискретные телепортации; заполнение следует внутренней геометрии труб, с согласованным движением фронта, масками, объёмом, брызгами и прозрачностью.
4. **Без потери объектов при анимациях:** никакая труба, пробирка/резервуар или интерактивный элемент не исчезает при повороте, перемещении, масштабировании, восстановлении или завершении испытания.
5. **Никаких фиктивных реализаций:** декоративные кнопки, незаполненные обработчики, подмена сложных механик роликом либо placeholder-графика не являются выполнением финального ТЗ. **Во время разработки** обязательны работающие программные заглушки-примитивы, когда финальные изображения недоступны; их нельзя принимать за утверждённую графику.
6. **Сначала исследовать существующее:** стек, каталоги, Phaser, PWA/service worker, роутинг, хранилища, сервер, конфигурацию и контракты MiniGames. Не исходить из предположения, что новый backend или общий SDK отсутствуют.
7. **Все обязательные функции включены в окончательный результат:** поэтапность — способ организации разработки, не основание урезать содержание.

### 1.2 Что НЕ требуется сейчас

- Интернет-магазин, платежи, подписки, реальные деньги и реклама (только проектная готовность к подключению общеплатформенной монетизации позднее).
- Публичная библиотека пользовательских уровней и пользовательский редактор: **редактор нужен только разработчику**.
- Полноценный градостроительный симулятор, собственный музей с навигацией, многопользовательский PvP, публичные рейтинги, обязательные серии посещений.
- Реалистичные давление, гравитация, вязкость, CFD или сложная химическая модель цвета.
- Массовое создание отдельных backend-микросервисов без обоснованной необходимости.

## 3. Архитектура системы

### 3.1 Логические слои

```text
MiniGames PWA / существующая оболочка
├─ Каталог, навигация, профиль, i18n, доступность, уведомления
├─ Game SDK / игровой контракт (общий для всех игр)
│  ├─ Lifecycle: load / mount / pause / resume / unmount / dispose
│  ├─ Persistence: save / restore / migrations / offline sync
│  ├─ Events: level completed / failed / achievements / errors
│  └─ Shared services: audio / preferences / auth / logging
├─ Games
│  ├─ «Переливашки» (адаптированы к контракту, механика неизменна)
│  └─ «Водопроводчик»
│     ├─ domain: чистая детерминированная модель
│     ├─ simulator: пошаговые массовые балансы и команды
│     ├─ generator: seed → задачи
│     ├─ solver: поиск / сертификация решений
│     ├─ progression: режимы, мастерство, адаптация
│     ├─ phaser: сцены, камера, управление, анимации, звук
│     ├─ ui: цели, обучение, подсказки, результаты, коллекции
│     ├─ assets: атласы, маски, звуки, диорамы / PLACEHOLDER fallback
│     └─ adapters: SDK, сохранения, ежедневные задания
├─ Developer-only AssetGen (OpenCode skill + субагент + очередь + QA + атласы)
│  ├─ GPT Image API adapter / reviewer / approved StyleBible
│  ├─ programmatic primitives when API unavailable
│  └─ status registry / replacements / integration visual QA
└─ Server (общий, модульный)
   ├─ Auth / email OTP / гостевые привязки
   ├─ Player & Game Saves / Sync / Event Idempotency
   ├─ Achievements / Collections / Challenges
   ├─ Remote Config / Admin / Audit / Analytics
   └─ API & storage
```

Это **логическая схема**, а не приказ создать новые папки с такими именами. Физическую структуру подогнать под репозиторий после аудита.

### 3.2 Главные архитектурные инварианты

- **Модель предметной области, генератор и решатель не зависят от Phaser, DOM, canvas, кадров/таймеров визуализации и сети.** Их можно запускать в Node и тестах без браузера.
- Симуляция использует фиксированные логические шаги и целочисленные дискретные порции жидкости. Рендер интерполирует между логическими состояниями.
- Один источник истины для правил игры; generator/solver/renderer не должны иметь противоречащих копий правил. Валидатор результатов обязан независимо воспроизводить действия через официальную модель.
- Генерация, симуляция, проверка решений и воспроизведение событий детерминированны для одних и тех же `rulesetVersion`, `generatorVersion`, `seed`, исходного состояния и команд.
- Игровые модули загружаются по требованию; после завершения освобождают scene-объекты, текстуры, listener-ы и ресурсы, не используемые другими играми.
- Общие аккаунты, настройки, уведомления, аналитика и монетизационные точки расширения — **в платформе**, не копии на каждую игру.
- Графические и аудиоэффекты не имеют права влиять на исход логики и скорость внутриигрового физического времени.

### 3.3 Игровой контракт (пример семантики, адаптировать к существующему SDK)

```ts
interface MiniGameModule {
  id: 'plumber';
  version: string;
  metadata: { titleKey: string; icon: string; offlineBundle: string };
  load(context: MiniGameServices): Promise<void>;
  mount(container: HTMLElement, restore?: VersionedSnapshot): Promise<void>;
  pause(): Promise<void>;
  resume(): Promise<void>;
  captureState(): Promise<VersionedSnapshot>;
  unmount(): Promise<void>;
  dispose(): Promise<void>;
}

interface MiniGameServices {
  profile: ProfileService;
  persistence: SaveService;
  achievements: AchievementsService;
  audio: AudioService;
  locale: LocaleService;
  accessibility: AccessibilityService;
  telemetry: ConsentAwareTelemetry;
  navigation: NavigationService;
}
```

Сигнатуры — **иллюстрация контракта**, а не требование менять уже существующие интерфейсы. Зафиксировать и документировать итоговый реальный API. У `load/mount/unmount/dispose` должны быть проверяемые гарантии идемпотентности и отсутствия утечек.

## 4. Модель уровня и состояние игры

### 4.1 Разделить три сущности

1. **`LevelDefinition` (неизменяемо):** исходная задача, цели, правила, параметры генерации, стартовый инвентарь и ограничения.
2. **`RuntimeState` (изменяемо):** текущее расположение/ориентация труб, клапаны, содержимое сегментов, остатки в источниках, программы, получатели, текущая фаза.
3. **`PlayerRecord` (долговременно):** режим, освоенные механики, оценки, достижения, результаты испытаний и настройки, независимые от конкретного `RuntimeState`.

Обязательные поля `LevelDefinition` (названия примерные): `schemaVersion`, `rulesetVersion`, `generatorVersion`, `puzzleId`, `seed`, `mode`, `difficultyScore`, `family`, `unlockedMechanics`, `grid`, `blockedCells`, `initialPipes`, `sources`, `receivers`, `inventory`, `controlModes`, `objectives`, `resourceLimits`, `themeId`, `solutionWitness`, `difficultyEvidence`. Раздельно хранить машинный экземпляр и отображение UI.

`RuntimeState` хранит точную модель, в том числе фазы испытания, значения дозирования и команд, прогресс внутри анимационно отображаемых операций, если это необходимо для согласованного восстановления. **Нельзя** рассчитывать реальное состояние воды по последнему нарисованному кадру.

Уровень однозначно идентифицируется не одним номером и не одним `seed`, а комбинацией уникального `puzzleId` и зафиксированных версий правил/генератора/конфигурации. Для долгосрочной устойчивости хранить **полный нормализованный LevelDefinition** незавершённого и расшариваемого уровня; один seed с версиями служит для проверки воспроизводимости, не единственной гарантией.

### 4.2 Сетка и элементы

- Прямоугольные и квадратные сетки, заблокированные клетки и произвольная доступная область в рамках сетки.
- Источники/получатели вначале на краях, позже допускаются внутри поля и в нескольких экземплярах.
- Семейства труб: прямая, угловая, Т-образная, крестообразная, заглушка; вращаемая и неподвижная; отдельные однонаправленные каналы; клапан, кран, переключатель, распределитель, разделённое пересечение, фильтр и смеситель.
- У каждой трубы явно определены порты по сторонам клетки, направление/допустимость входа и выхода, внутренняя вместимость, каналы и режим интерактивности; у перекрёстных изолированных труб две независимые дорожки.
- Инвентарь и перенос труб раскрываются после механики вращения. В уровне явно указан набор разрешённых операций.
- Игровые получатели: автоматически перекрывающиеся после наполнения; открытые переливающиеся; точного объёма с ошибкой при превышении; накопительные резервуары с регулируемой отдачей.
- Тема сцены зависит от задачи (сад, фонтан, посёлок, промышленный объект и т. д.), но не от другой модели физики.

### 4.3 Действия и фазы

Базовые команды: `Rotate`, `Select`, `Pickup`, `Place`, `ToggleValve`, `SetDistributor`, `StartTrial`, `PauseTrial`, `ResumeTrial`, `StopTrial`, `RestartTrial`, `StepTrial`, `AppendProgramCommand`, `ReorderProgramCommands`, `Undo`, `Redo`, `RequestHint`, `ShowSolution`, `SkipLevel`. Варианты и разрешения определяются механикой/фазой уровня, не глобальным набором доступных кнопок.

Фазы: `PREPARING → RUNNING ↔ PAUSED → (WON | FAILED | STOPPED)` с явным возвращением к `PREPARING` для очередной попытки. Для динамических задач часть действий разрешена в `RUNNING`, в остальных — нет. Каждое состояние должно иметь чёткие входы/выходы, запрет недопустимых команд и тесты прерывания.

**Правило по умолчанию:** поворачивать/переносить участок, содержащий жидкость, нельзя в активном испытании, если конкретная механика уровня не объявляет и не реализует способ безопасного обращения с жидкостью. Переключение предусмотренных динамических клапанов допустимо. Нельзя тихо «очищать» трубу при перемещении.

Остановка/повтор: состояние **сборки** труб сохраняется, а ресурсы испытания и жидкость возвращаются в зафиксированное состояние начала попытки. При отмене изменений во время непрерывного испытания откат работает только если команда и её последствия полностью записаны; нельзя сохранять частичный массив визуальных частиц как модель уровня. Повтор победы не начисляет награды повторно.

## 5. Семантика жидкости и детерминированная симуляция

### 5.1 Обязательные правила

1. Вода движется **в любом направлении** по соединённым портам. Гравитация, гидравлическое давление и реалистичная вязкость **не моделируются**.
2. Вода существует в **целочисленных порциях**, каждая порция имеет тип/цвет. Для смесей используются дискретные рецепты, включая пропорции.
3. **Закон сохранения объёма:**

   `источники_в_начале + явно созданные внешние порции = источники_сейчас + трубы + буферы + получатели + потери_через_явные_стоки/утечки`.

   Для бесконечных источников учитывать фактически введённые порции. Никакие ответвления, петли, анимации, смешивания и пересечения не создают/не уничтожают объём скрыто.
4. Система имеет фиксированный дискретный `tick`. Заявки на передачу порций формируются из единого snapshot начала тика; резервирование ёмкости и распределение выполняются **до** атомарного применения переносов, чтобы порядок обхода массивов не влиял на результат.
5. При нескольких выходах обычной трубы объём распределяется максимально равномерно. Остаток при неделимом объёме распределяется по **стабильному документированному порядку портов**, независимому от FPS, platform и времени суток. Клапаны закрывают пути; распределитель задаёт пропорции (например, 70/30) с детерминированным округлением.
6. Вместимость каждой трубы ограничена. При полном участке новая порция остаётся в предыдущем сегменте/источнике до появления места, если правила не устанавливают утечку/перелив. Нельзя терять воду от переполнения памяти модели.
7. Два потока **одинакового** типа могут объединяться при наличии вместимости. В обычном общем канале встреча **разных** типов — ошибка с детерминированным завершением/маркером, если уровень не разрешает специальный смеситель; через изолированное пересечение жидкости проходят независимо.
8. Цветные жидкости в обычных трубах не смешиваются. Фильтры пропускают предусмотренные типы/составы по конфигурации; смеситель трансформирует заданное количество входных порций в ровно такое же суммарное количество выходных порций по **явной таблице рецептов**.
9. Замкнутые контуры разрешены. При заполнении без доступных выходов поток прекращается. Нет бесконечной циркуляции, дублирования и бесконечного цикла обработчика. Цикл с выходом может продолжать отдачу при наличии физически допустимого по правилам места/объёма.
10. Получатели принимают строго по собственному типу. Автозакрытие, переполнение с явным сливом, ошибка точного дозирования и буферная отдача реализованы как состояния модели, а не как визуальные эффекты.
11. Пошаговая симуляция должна гарантированно завершаться или корректно останавливаться на состоянии стабильного равновесия/неизменности в пределах заранее определённого, проверенного ограничения, без ложной победы.
12. У разных целей могут быть требования по объёму, цвету, рецепту, герметичности и использованию специальных элементов. Все условия известны игроку перед запуском.

### 5.2 Работа смесителя

Модель рецепта, например `{red: 2, blue: 1} → {purple: 3}`. Входные порции расходуются только при наличии всех обязательных компонентов и свободной выходной ёмкости. Последовательное смешивание нескольких цветов и многоступенчатые рецепты поддерживаются на более поздних уровнях. Оттенки не вычисляются случайным RGB-смешиванием. Одинаковое входное состояние всегда даёт одинаковый результат.

### 5.3 Разные режимы испытания

- **Статический:** редактирование до старта, во время движения только наблюдение/разрешённое управление паузой.
- **Управляемый:** пауза/продолжение/остановка/повтор/ускорение визуализации.
- **Динамический:** некоторые клапаны и переключатели меняются при движении воды; семантика проверяется моделью на каждом тике.
- **Ресурсный:** фиксированные объёмы, потери и дозирование значимы для цели.
- **Программируемый:** визуальный список дискретных команд источникам и клапанам; исполнение на логических шагах, не по миллисекундным таймингам.

### 5.4 Управление источниками и программами

Прогрессия: одиночная общая кнопка → одновременный запуск нескольких источников → управление отдельными кранами → управление последовательностью → программируемая последовательность в экспертных задачах. Визуальные команды включают `Feed(sourceId, integerPortions)`, `SwitchValve(valveId, state)`, `ToggleSource(sourceId, state)` и последовательное выполнение. Блоки переставляются; исполнитель показывает активный блок и изменившийся результат. **Нет** обязательных циклов, условных операторов и временной шкалы реальных секунд: это не было выбрано.

## 6. Генерация уровней, решатель, звёзды и адаптация

### 6.1 Бесконечный генератор

После победы всегда существует следующий процедурный уровень. В качестве целевых семейств использовать: составление пути; исправление утечек; многопотребительские сети; прохождение препятствий; закрытые/односторонние пути; точное дозирование; цветовые маршруты; рецептурное смешивание; динамические клапаны; блоковые программы. Семейства включаются только после обучения соответствующим механикам.

Обязательный pipeline:

1. Выбрать режим (`child | normal | expert`), освоенные механики, семейство, целевой профиль сложности и допустимый размер сетки.
2. Выбрать детерминированный `seed` и зафиксировать версии алгоритмов и правил.
3. Построить **валидную завершённую систему** из маршрута/нескольких маршрутов, препятствий, допустимых источников/получателей и заданных ресурсных условий.
4. Добавить отвлекающие компоненты, ложные пути, повороты и перестановки, **не уничтожая существования решения**.
5. Запустить автоматический решатель/валидатор; проверить цель, расходы, отсутствие нежелательного тривиального обхода и сложность.
6. Проверить недавние головоломки на чрезмерное структурное сходство, включая повороты/отражения, близкие наборы действий и одинаковые паттерны.
7. Сохранить определение уровня, свидетельство решения и данные сложности. При неудаче использовать другую стратегию генерации с ограниченным бюджетом вычислений.

Запрещено просто выдавать непроверенную случайную схему. Если допустимый уровень не найден в пределах вычислительного бюджета — использовать заранее рассчитанный **валидный** резервный шаблон того же диапазона/семейства либо безопасно снизить сложность, уведомив систему адаптации. Интерфейс не должен блокироваться длительным поиском; использовать worker/асинхронную подготовку там, где это оправдано существующим стеком.

### 6.2 Решатель

- Работает с теми же формальными правилами, что и игра, но независим от графики и эффектов.
- Умеет учитывать операции вращения, перемещения, установки, клапаны, распределители, дозирование и составление дискретной программы; поисковое пространство ограничивается разрешёнными операциями **конкретного уровня**.
- Возвращает не только `solvable`, но и **проверяемую последовательность команд**; валидатор отдельно воспроизводит её в симуляции до реальной победы.
- Для звёзд/оценки эффективности использовать достоверный оптимум или доказанный достаточный ориентир с явно заданными границами. Если доказать пригодную оценку нельзя, не публиковать уровень в режиме, где звёзды несправедливо зависят от недоказанного количества ходов.
- Подсказки рассчитываются **от текущего состояния пользователя** и предлагают разрешённое корректное действие. Не заставляют возвращаться к единственному авторскому маршруту.
- Учитывать несколько допустимых решений. Любое удовлетворяющее условиям — победа.
- Изолировать тяжёлый поиск от рендера, ограничивать время и память, собирать метрики неудачных попыток.

### 6.3 Режимы сложности и освоение

- Три режима: **детский**, **обычный**, **экспертный**. У каждого независимый прогресс и статистика.
- Адаптация внутри режима по попыткам, результатам, подсказкам, количеству действий, времени и частоте пропусков. Детский режим не штрафует за время.
- Новые механики открываются по последовательности с проверкой освоения; нельзя бесконечно задерживать открытие. При затруднениях дать доступное обучение и более простые задачи, сохраняя уже открытое.
- Размер поля ограничен удобством на физическом экране. Генератор должен учитывать фактическую область, доступную при приемлемой области касания; на большом поле включать камеру/масштабирование вместо микроскопических клеток.
- Три звезды привязаны к эффективности решения относительно проверенных свойств **конкретного** уровня. Ошибки и использование подсказок регулируются прозрачными правилами; прохождение возможно и с одной звездой.
- Ведение статистики, лучших решений, попыток и времени; недопустима разница из-за FPS или частоты тиков рендера.

### 6.4 Подсказки и пропуск

`Undo/Redo`, подсветка проблемного участка, подсветка трубы и конкретного действия, демонстрация решения, пропуск без блокировки прогресса. После нескольких неудачных действий можно ненавязчиво предложить помощь. Генератор следующего уровня учитывает затруднения; в обучении нет обязательного чтения.

## 7. Управление, интерфейс и визуальное обучение

### 7.1 Игровые жесты

- Короткое нажатие — поворот доступной трубы на 90° с плавной анимацией без смещения центра.
- Долгое нажатие — захват разрешённой трубы и перенос; допустимые клетки подсвечены.
- Из инвентаря: drag-and-drop **или** выбрать элемент и целевую клетку. Для доступности перенос без жестов обязателен.
- Мышь и клавиатура — полнофункциональные альтернативы; для компьютера камера допускает перемещение и масштабирование колесом/доступными клавишами.
- Сенсорное масштабирование двумя пальцами и панорамирование поля не конфликтуют с поворотом/переносом. Состояния жестов взаимно исключены и имеют корректную отмену.
- Недопустимые операции объясняются понятным визуальным сигналом, но не меняют модель.

### 7.2 Адаптивная компоновка

Портрет/ландшафт, смартфон/планшет/desktop. На маленьких экранах поле в приоритете, контекстные кнопки в зоне доступности большого пальца; на широких — возможна боковая панель. Пауза, настройки и выход всегда доступны. Учитывать вырезы/безопасные зоны; при повороте устройства состояние игры сохраняется. Большое поле — pinch/pan, reset-to-fit; автогенератор не должен делать интерактивные зоны чрезмерно мелкими.

### 7.3 Состояния интерфейса

Во время подготовки — цели, трубы, инвентарь (если нужен), отмена и запуск. Во время испытания — акцент на жидкости, допустимые действия, пауза/остановка. При неудаче — место ошибки, повтор и помощь; при победе — объекты окружающего мира оживают, появляются звёзды, продолжение и просмотр результата. Не перекрывать поле лишними модальными окнами.

### 7.4 Система целей без чтения

Получатели показывают цвет, символ/узор, количество порций и требования. При первом появлении правила игра показывает короткую анимацию. Панель целей компактно показывает состояние; по нажатию выделяются относящиеся к цели объекты. Цели создаются автоматически из структурированных полей `LevelDefinition`, а не из захардкоженных текстов на спрайтах.

### 7.5 Онбординг

Система интерактивных мини-уроков непосредственно в реальной головоломке: визуально показать действие → дождаться действия игрока → дать отклик → при задержке подсветить → при необходимости показать анимированный палец. При повторной встрече изученной механики урок пропускается; обучение не должно становиться отдельной цепочкой текстовых карточек. Все этапы и три режима должны пройти тест «без чтения».

### 7.6 Доступность и локализация

- Русский и английский с первого релиза. Строки отдельно в таблицах локализации, переключение без сброса уровня, расширение языков без переписывания правил.
- Цвет **не единственный** носитель информации: узор/символ, контраст, пиктограммы порций и обозначения типов.
- Доступны высокая контрастность, увеличенные элементы, снижение анимаций, отключение вспышек, регулировка скорости демонстрации воды, управление без перетаскивания, клавиатура, настройка удержания.
- Не использовать интенсивное мигание и стробоскопические эффекты по умолчанию.
- Настройки общего назначения через SDK MiniGames, уникальные настройки жидкости — локально в профиле игры.

## 8. Графический конвейер, вода, звук и окружение

### 8.1 Стиль

**Стилизованный 2.5D** без обязательного 3D-движка: оригинальные качественные трубы с объёмом, мягкими тенями, бликами и полупрозрачной внутренней частью. Компоненты соседних труб точно совпадают по портам; вращение не приводит к визуальным разрывам, наложениям, появлению двойных контуров или исчезновению объектов.

### 8.2 Производство ассетов

- Подготовленные 2.5D-спрайты и атласы: прямая/угловая/Т-/крест, заглушка, клапаны/краны/распределители/фильтры/смесители, источники и получатели.
- Машиночитаемые метаданные спрайта: `ports`, ось/центр вращения, видимые каналы, маска внутреннего объёма, точки эффектов, слои отрисовки, states.
- Воду анимировать процедурно **в маске внутреннего канала** и с учётом её фактического уровня по сегментам, а не рисовать внешнюю линию поверх всех труб.
- Частицы брызг/капель/пузырьков и блики — отдельные слои, не влияющие на логику, не заслоняющие интерактивные зоны и не создающие видимого неверного маршрута.
- Окружение определяется типом задач: сад, посёлок, фонтан и др.; объекты реагируют на поток и победу, но не добавляют скрытых условий.
- Исходники, лицензии и права на ассеты документировать. В приёмке нет заглушек. Если качественный ресурс технически недоступен, это открытый блокер **финальной визуальной приёмки**. Для непрерывности разработки AssetGen при этом **обязан** создать временные корректные примитивные изображения (трубы, клапаны, источники, цели, окружение) с явным статусом `PLACEHOLDER` и рабочими `ports`, pivot и масками. Заглушки ни при каких условиях не считаются финальной графикой.

### 8.2.1 Обязательный AssetGen и политика временной графики

Полная нормативная спецификация: **`03_ASSETGEN_AGENT_SPEC.md`**. Проектный OpenCode skill: `.opencode/skills/minigames-assetgen/SKILL.md`, специализированный субагент: `.opencode/agents/assetgen.md`.

- Основной OpenCode делегирует заявки AssetGen по формализованному `AssetRequest` и принимает только отчёты с подтверждённым статусом и путями к реальным файлам.
- AssetGen пытается произвести художественный ресурс через **доступный и явно настроенный GPT Image API**, затем проверяет прозрачность, художественный стиль на утверждённых референсах, точность соединений и пригодность в Phaser; при отказе инициирует ограниченную перегенерацию. Простая проверка наличия alpha не заменяет визуальную оценку.
- Конвейер нормализует PNG, нарезает только по проверенным координатам, собирает атласы и JSON-метаданные, отделяет художественные спрайты от детерминированной геометрии каналов и масок жидкости.
- **Если Image Gen не может отрисовать ассет (нет доступа, лимиты, неудачная проверка, неполный пакет), сразу создать и подключить программный `PLACEHOLDER`** правильного типа. Примитивы — линии/контуры/простые фигуры, но с корректными интерактивными портами, hitbox и условными водяными каналами. Это **обязательная fallback-функциональность**, а не право пропустить ассет.
- Пока ассет отсутствует, OpenCode продолжает логическую, серверную, PWA-, тестовую, UX- и интеграционную разработку с заглушкой. В матрице отмечаются отдельно готовность игровой механики и незакрытая художественная часть. Не ждать пассивно, не пытаться обходить квоты и не расходовать API без подтверждённых разрешений/бюджета.
- Финальный release-gate запрещает `PLACEHOLDER`; он закрывается **только** при замене и фактической визуальной проверке готовых ассетов.
- Учесть, что квоты ChatGPT не равны квотам API; наличие OpenCode **не подразумевает доступ** к GPT Image. Повторная отправка после 429 — лишь при соблюдении лимита и при действительно запущенном worker/повторном вызове.

### 8.3 Качество и производительность

Цель 60 FPS на подходящих устройствах, допустимое упрощение до 30 FPS на слабых. Измерять фактические частоты в выбранных аппаратных/эмулированных профилях. Автоматически понижать количество частиц, шейдерные эффекты, разрешение динамических слоёв и блики без изменения модели воды. При `visibilitychange`, сворачивании PWA и возврате не должно возникать рывков логики, пропавших труб или двойного начисления событий. `reduce motion` сохраняет информативное движение, но убирает лишние эффекты.

### 8.4 Звук

Общая аудиосистема MiniGames: механические повороты, клапаны, журчание, переливы/утечки, победа; спокойная музыка; настройки музыки, SFX и вибрации отдельно; пауза при сворачивании. Пространственные эффекты и суммарный звук воды — **не один звуковой канал на каждую трубу**. Поддерживаемая тактильная отдача необязательна; воспроизведение звука — только после разрешённого пользовательского взаимодействия.

### 8.5 Анимация победы

Сначала доменная модель подтверждает победу; затем вода заканчивает свой путь и окружение реагирует: распускается цветок, запускается фонтан, загорается дом и т. п. Неблокирующие звёзды и кнопка следующего уровня появляются поверх текущей сцены. Анимацию можно пропустить, награды должны начисляться единожды независимо от её полного просмотра.

## 9. Коллекции и достижения

- Основной прогресс — число пройденных уровней по режимам, лучшие решения и звёзды.
- Тематические альбомы: **сад, город, промышленность, особые проекты**.
- **12–16 уникальных объектов** первой версии, некоторые имеют визуальные варианты. Новые каталоги подключаются версиями без потери ранее открытых предметов.
- Открытие предметов связано с соответствующими головоломками и достижениями; без случайных дублей, лутбоксов и платных предметов.
- Альбом отображает полученные объекты полноцветно и анимированно, ещё закрытые — силуэтами. Можно просмотреть каждый объект.
- Завершение альбома открывает отдельную анимированную **диораму**, объединяющую объекты коллекции, с возможностью повторного просмотра.
- Не строить постоянный город, магазин, свободный музей или публичные рейтинги.
- Коллекционные награды идемпотентны при повторе и синхронизации.

## 10. Offline-first, аккаунт, сохранения и синхронизация

### 10.1 Пользовательский путь

Первый запуск — **сразу гостевая игра**, без регистрации. Основной вход в единый аккаунт MiniGames — одноразовый код на электронную почту. В будущем архитектура может принять других провайдеров, но это не обязательная реализация сейчас. При привязке гостя локальные сохранения объединяются с серверными без потерь. Профиль платформы общий для игр; результаты «Водопроводчика» хранятся отдельно от «Переливашек». Для детей не запрашивать лишние личные сведения; предусмотреть необходимые ограничения на обработку данных детской аудитории.

### 10.2 Локальные сохранения

Рекомендуемое хранилище — IndexedDB либо уже существующее пригодное хранилище MiniGames. Автосохранение после **каждого подтверждённого логического изменения**, а также при паузе, закрытии, переходе в фон. Сохранять `LevelDefinition`, `RuntimeState`, журналы/снимки для Undo/Redo, прогресс освоения, режим, коллекции, результаты и локальную очередь синхронизации. Состояние во время воды восстанавливать через согласованный снимок симуляции: **без** потерянных/удвоенных порций и внезапно исчезнувших объектов.

### 10.3 Синхронизация

- События имеют стабильные UUID/идентификаторы, последовательность и версию схемы; отправка повторно безопасна.
- Уровневые достижения объединяются по уникальному `puzzleId`/режиму; лучший результат сохраняется по прозрачному правилу, коллекции — объединение множеств.
- Агрегированную статистику пересчитывать из уникальных событий, не суммировать повторяющиеся отчёты разных устройств.
- Незавершённые разные состояния уровня нельзя слепо перезаписывать: сохранить обе ветки/снимка и дать пользователю понятно выбрать, если автослияние невозможно.
- Настройки конфликтуют по отдельным ключам. Миграции и применение синхронизации должны быть транзакционными и с откатом.
- Сервер выборочно воспроизводит важные достижения по исходному состоянию и действиям; обычный игровой процесс не зависит от наличия сервера. Клиентское офлайн-свидетельство не рассматривается как криптографически неоспоримое.

### 10.4 Версии и обновления

Версионировать **по отдельности** игру, `LevelDefinition`, сохранения, генератор и правила симуляции, коллекции/каталог и конфигурацию. Перед миграцией создавать восстановимую копию. При обновлении не прерывать активный уровень; после обновления восстановить с прежними трубами, жидкостями и условиями. Для старых незавершённых уровней допускается ограниченный механизм совместимости правил. При критической ошибке — откат.

### 10.5 PWA, кэш и сборки

- Использовать существующий домен, маршрутизацию, HTTPS, web manifest и один согласованный service worker/scope MiniGames. Не создавать вторую конфликтующую PWA.
- Shell платформы кэшируется для офлайн-запуска после первичной установки. Игры загружаются лениво.
- Для каждой игры поддерживаются: частичное кэширование при запуске, **полная загрузка для офлайн**, индикация состояния и удаление кэша игры **без** удаления прогресса.
- Дополнительные ассеты коллекций и окружения загружаются по необходимости. Статус «доступно офлайн» ставить только после фактической проверки полной доступности обязательных файлов и логики.
- При нехватке квоты хранилища давать информативный сценарий; браузер вправе вытеснить данные, поэтому авторизованным пользователям нужна серверная синхронизация.
- Обновления разных версий ассетов должны быть атомарно согласованы с соответствующей версией игры; нельзя смешивать старые скрипты с новыми правилами.

## 11. Backend MiniGames, API и безопасность

Общий **модульный backend**, не самостоятельный backend каждой игры. Если его нет, использовать Node.js + TypeScript + Fastify + PostgreSQL. Предварительно исследовать существующий код и миграции. Названия endpoint-ов ниже **примерные**, итоговый контракт должен соответствовать текущей архитектуре.

| Группа | Пример API/операции | Требования |
|---|---|---|
| Auth | `POST /auth/otp/request`, `POST /auth/otp/verify` | ограничение частоты, срок действия одноразового кода, защита от перебора и перечисления адресов |
| Profile | `GET /me`, `POST /guest/link` | единая идентичность MiniGames, безопасное слияние локальных и серверных данных |
| Saves | `GET /games/:id/save`, `POST /games/:id/sync` | версии данных, идемпотентные события, контроль конфликтов |
| Achievements | `GET /games/:id/achievements` | уникальное начисление и аудит изменений |
| Challenges | `GET /games/:id/challenges`, `GET /.../:challengeId` | подписанные/проверяемые идентификаторы, доступ к архиву, UTC-расписание |
| Share | разрешить/открыть код уровня | корректная нормализация данных, ограничение размеров и частоты запросов |
| Config | `GET /games/:id/config` | версионный read-only публичный срез с правилами совместимости |
| Admin | конфигурации, валидация, предпросмотр, публикация, rollback | роли/права, журнал аудита, CSRF/авторизация, изоляция от пользовательского API |
| Telemetry | согласованные события | согласие, исключение персональных полей, безопасный лимит payload |

Нужны миграции БД с проверками и откатом; секреты только в серверном окружении; HTTPS; защищённые сессионные механизмы; ограничение запросов; контроль доступа по владельцу сохранения; логирование без паролей/OTP/лишних персональных данных; резервное копирование и процедура восстановления. Не выводить порт PostgreSQL в публичный интернет. Не менять чужие сервисы VPS без согласования.

## 12. Ежедневные и еженедельные испытания, обмен уровнями

### 12.1 Испытания

- Ежедневно — короткая одинаковая задача для игроков выбранного режима. Еженедельно — более сложная общая задача.
- Глобальные границы: **00:00 UTC ежедневно** и **понедельник 00:00 UTC еженедельно**.
- Сервер заранее генерирует, проверяет и публикует испытания; PWA кэширует несколько будущих задач. Офлайн-прохождение разрешено, если задача скачана заранее.
- Архив доступен без наказания за пропуск, но результат «в срок» и архивный должны различаться.
- Не начислять повторно награды при изменении часов, таймзоны или повторном запросе; использовать уникальные IDs challenge+player+mode.
- Если офлайн нет подготовленного задания — остаётся доступен бесконечный режим; нельзя показывать случайный уровень как общий ежедневный.

### 12.2 Обмен

- Шаринг конкретного **проверенного генератором** уровня по deep link в MiniGames и короткому коду.
- Ссылка фиксирует уровень/версию/правила (через идентификатор серверного манифеста или проверяемый компактный payload), работает в браузере и установленной PWA.
- Шаренные прохождения записываются отдельно от бесконечной персональной прогрессии. Отсутствуют пользовательский редактор, общедоступная библиотека и вызовы-соревнования.
- При недоступности нужной версии уровня показать корректный сценарий, не подменять содержание другим seed.

### 12.3 Уведомления

Внутри MiniGames — индикаторы новых задач. Push отключён по умолчанию, настройка ежедневных/еженедельных напоминаний отдельно, запрос системного разрешения только по инициативе пользователя. Детским пользователям не предлагать внешние уведомления по умолчанию. Функция должна деградировать до внутриигровых индикаторов в неподдерживаемых браузерах.

## 13. Административная панель, аналитика и инструменты разработчика

### 13.1 Панель администратора

Общая для MiniGames: каталог игр, доступность модулей, настройка вероятностей семейства/механик, сложности, коллекций, достижений, расписания испытаний, агрегированной статистики и технических ошибок. Конфигурация: **черновик → предпросмотр на репрезентативных seed → автоматическая проверка → публикация версии**. Нужны история, автор изменений, права доступа, откат. Новая конфигурация применяется только к новым головоломкам; существующие хранят оригинальные правила/параметры.

### 13.2 Аналитика

Технические метрики: сбои, генерация, FPS, загрузка, использование памяти, ошибки сохранений и синхронизации. Игровые (при соответствующем согласии): completion rate по семействам/режимам, частота подсказок, пропусков, освоения механик, время решения, возвращаемость. Минимизировать данные, отделять локальную адаптацию от серверного сбора, ограничивать сроки хранения, исключить персональные сведения из события там, где они не нужны. Диагностический файл пользователя отправляется только отдельным действием/разрешением. В серверной части предусмотреть управление согласием и правила для детской аудитории.

### 13.3 Developer tools (не публичный UI)

- Визуальная карта портов, каналов, объёмов, рецептов и движения воды.
- Панель `seed`, уровневых версий, параметров генерации, FPS, памяти.
- Ручной **редактор уровня для разработчиков**, прогон решателя и условий победы.
- Пошаговая симуляция, пауза, изменение скорости визуализации.
- Запись семантических команд и воспроизведение с контрольной суммой итогового состояния.
- Экспорт/импорт диагностики: определение уровня, версии, состояние, trace действий, нарушения инвариантов, только безопасные данные без авторизационных секретов.
- Пакетный поиск ошибок и сохранение проблемных seed в регрессионном наборе.
- Инструменты в production отключены или недоступны обычным игрокам.

## 14. Развёртывание и эксплуатация

- Сначала инвентаризовать VPS, текущие приложения, порты, контейнеры, веб-сервер, резервные копии и доступные ресурсы; произвести снимок/экспорт конфигурации перед работой.
- Если есть Docker — отдельный Compose-проект/неймспейс. Если есть общий reverse proxy — корректно подключиться к нему; если нет инфраструктуры, предусмотреть изолированное Docker Compose-развёртывание. **Не перезапускать чужие контейнеры/сервисы.**
- PWA и API доступны по HTTPS с доверенным сертификатом и в пределах одного согласованного доменного пространства; установка каждой новой игры не требует нового домена.
- PostgreSQL — внутренний сетевой контур, миграции с резервной копией; секреты вне репозитория.
- Минимальные healthchecks, логи, метрики, ограничение диска, резервное копирование, восстановление и rollback предыдущей работоспособной версии.
- Обновление «Водопроводчика» не нарушает игру «Переливашки», её пути, сохранения, графику, PWA и service worker.
- На продуктивный сервер **не делать опасных или несовместимых изменений без предусмотренного регламентом согласования**.

## 15. План обязательных этапов разработки

Результат каждого этапа — работающее состояние проекта, автотесты, короткий отчёт и контрольная точка в репозитории. При наличии критических дефектов следующий этап не начинать.

### Этап 1. Аудит, контракт, чистое ядро

- Аудит существующих MiniGames/«Переливашек».
- Согласование единого plugin-контракта и структуры пакетов.
- Типизированные `LevelDefinition`, `RuntimeState`, action log, схемы сохранения.
- Трубы, сетка, порты, базовые операции, простая дискретная симуляция.
- Детерминированный PRNG, начальный генератор и решатель, тестовый replay.
- Unit/property tests инвариантов.

**Гейт:** генерируемые базовые уровни доказуемо решаются, симуляция воспроизводима без браузера, прежние игры запускаются.

### Этап 2. Играбельность, качественная графика и онбординг

- Phaser-сцены, управление касанием/мышью/клавиатурой, адаптивная камера.
- Подключение AssetGen: задания на 2.5D-ассеты, проверка alpha/стиля, подготовка масок/атласов; при отсутствии генератора — **обязательные программные примитивные заглушки**. Полноценная масочная анимация воды, утечки, повороты, звук.
- Ручной запуск, ошибки, победа, подсказки и интерактивное обучение без текста.
- Локальное автосохранение, recovery, настройки и доступность.

**Функциональный гейт:** реальная игра и E2E на мобильном viewport работают, в том числе на примитивах; тесты симуляции и управления `PASS`. **Визуальный гейт:** реальные 2.5D-ассеты проверены в Phaser, видео анимаций зафиксированы, заглушек и исчезающих объектов нет. Если GPT Image недоступен, разрешено **продолжить независимые этапы 3–5**, сохранив визуальный гейт этапа 2 в статусе `BLOCKED_ASSET`; весь проект остаётся `PARTIALLY READY`, а этап 6 / релиз нельзя закрыть.

### Этап 3. Все сложные механики и проверяемый решатель

- Т-/крест, заглушки, препятствия, перенос/инвентарь, клапаны, фильтры, распределители, перекрёстные каналы.
- Несколько источников/получателей, все четыре типа получателей.
- Цветные жидкости, смесители, пропорции и дозирование, ресурсы, петли, столкновения.
- Динамические испытания, визуальные программы последовательной подачи.
- Генерация по семействам, адаптация, анти-повторы, корректная оценка звёзд.

**Гейт:** независимая batch-проверка и E2E по каждому семейству механик; разрешённые сценарии программы выполняются корректно; нет потери объёма.

### Этап 4. Прогресс, коллекции и спецрежимы

- Независимый прогресс трёх режимов, адаптация, подбор обучения.
- Альбомы на 12–16 оригинальных объектов, тематические диорамы и анимированная победа.
- Ежедневные/еженедельные испытания, архив, шаринг ссылкой/кодом, уведомления.
- Локальный кэш игр/ресурсов, офлайн-испытания, `ru/en` локализация.

**Гейт:** все награды и испытания корректно сохраняются, не дублируются, открываются без интернета после загрузки.

### Этап 5. Общая серверная инфраструктура MiniGames

- Переиспользование/доработка существующего backend; при отсутствии — согласованный запасной стек.
- Общий гостевой/OTP-аккаунт, безопасная привязка, sync & merge, миграции.
- Общие SDK-службы, push-настройки, API конфигурации, панель администратора, аналитика с согласием.
- Изоляция развёртывания, healthchecks, backup/restore, безопасные обновления и rollback.
- Подключение «Переливашек» к общему контракту без изменения механики.

**Гейт:** интеграционные тесты двух игр, двух устройств, офлайна и конфликтов; эксплуатационные тесты безопасного развёртывания.

### Этап 6. Полная приёмка и исправления

- Автогенерация и валидация массового набора уровней, stress/property tests.
- Визуальная регрессия и записи ключевых анимаций, тестирование управления/онбординга.
- Проверки производительности, памяти и офлайн/PWA-update flow.
- Тестирование i18n, accessibility, безопасности, миграций, аварий и отката.
- Матрица требований, акт результатов, скриншоты, видео, измерения, runbook развёртывания.

**Гейт:** нет невыполненных критических требований, нет известных критических дефектов, представлен проверяемый evidence pack. Невозможные к исполнению пункты явно помечаются и запрещают заявление «полностью готово».

## 16. Обязательные тесты и критерии приёмки

### 16.1 Проверка логики: обязательно автоматизированная

| ID | Сценарий | Критерий |
|---|---|---|
| CORE-01 | Один источник, правильный/неправильный путь | победа только при выполнении цели; место утечки/разрыва визуально соответствует модели |
| CORE-02 | Повороты, переносы, инвентарь, фиксированные трубы | только разрешённые действия меняют состояние; undo/redo согласованы |
| CORE-03 | Т- и крестообразные соединения, деление порций | детерминированные доли, суммарный объём сохраняется |
| CORE-04 | Два источника одинаковой жидкости | корректное объединение и ограничения вместимости |
| CORE-05 | Потоки разного типа в общем канале / изолированном пересечении | в общем — ошибка; при изоляции — независимое движение |
| CORE-06 | Смеситель и каскад рецептов | входные порции исчезают только в рамках сохранения массы, выход правильный |
| CORE-07 | Фильтры, однонаправленные трубы, клапаны и распределители | соблюдение направлений/типов/долей; нет протечек через закрытые элементы |
| CORE-08 | Петли, тупики, заполненные каналы | симуляция завершается/стабилизируется; без бесконечной циркуляции и воды из ничего |
| CORE-09 | Все четыре типа получателей | автозакрытие, перелив, точный объём, накопление/отдача |
| CORE-10 | Статический/динамический/ресурсный/программируемый режим | разрешённые команды в нужные фазы, запрет недопустимых действий |
| CORE-11 | Пауза, stop, restart, запись и replay | нет потерь/удвоения порций и расхождений между повторами |
| CORE-12 | Разные FPS / скорость отображения | один и тот же trace команд даёт битово/канонически равный итог модели |
| GEN-01 | Пакет **не менее 10 000 уровней** разных режимов/семейств/seed | все опубликованные примеры валидны; каждый принят только после проверки решателем |
| GEN-02 | Восстановление по `seed`+версии и полному LevelDefinition | тот же уровень/решение/свойства сложности |
| GEN-03 | Отбраковка повторов/зеркальных/структурных дубликатов | пороги и выбранное окно задокументированы, регрессионные примеры отклоняются |
| GEN-04 | Нехватка вычислительного бюджета | UI не зависает, выдаётся проверенный резервный уровень |
| SOL-01 | Несколько путей решения | любой корректный путь засчитывается, подсказки применимы к текущему состоянию |
| SOL-02 | Звёзды и эффективность | три звезды не присуждаются по недостоверной «оптимальности»; режим child не штрафуется за время |
| PROG-01 | Освоение/затруднения/три режима | адаптация работает, прогресс раздельный, новые механики разблокируются без бесконечных тупиков |

`10 000` — минимум суммарной пакетной проверки, **не** обещание доказать корректность всех возможных комбинаций. Обязательно добавить набор целевых property-based и ручных пограничных тестов. Сохранять seed каждого провала в regression fixtures.

### 16.1.1 Приёмка AssetGen и fallback (дополнение)

- В тестовом отключении доступа к генератору для 8 базовых видов труб/объектов автоматически создаются валидные примитивные PNG/Phaser Graphics с `is_placeholder=true`. Игра с ними запускается, поворачивает элементы, прокладывает и показывает воду; OpenCode продолжает функции вне художественного слоя.
- Примитивы и финальные ассеты хранятся раздельно; смена графики не изменяет `LevelDefinition`, портовые маски, collision/hitbox, историю игрока и сохранения.
- PNG с белым фоном, RGB без alpha, повреждённые изображения, неверные края/углы, обрезанные объекты отклоняются; автоматический отчёт фиксирует причины.
- Стилистическая проверка обязана использовать реальные эталоны и зрительный анализ/человеческую приёмку, а не гистограмму. Для финальной приёмки проверяются сцены Phaser и реальное движение жидкости в полых трубах.
- Повторные попытки ограничены, 429 ставится в `WAITING_FOR_LIMITS`, отсутствие ключа/оплаты — `WAITING_FOR_PROVIDER`. Статусы персистентны и доступны основному агенту.
- Пока существует хотя бы одна используемая финальной сценой заглушка или отсутствует проверка ассета, визуальный гейт `FAIL/BLOCKED`, финальная готовность `READY` невозможна.

### 16.4 Порог приемлемости и доказательства

- **Ноль известных блокирующих дефектов**: невозможность закончить валидный уровень, неправильная победа/начисление, потеря прогресса, бесконечная симуляция, уничтожение существующей игры, серьёзная ошибка доступа к чужим аккаунтам.
- Все обязательные UI-кнопки и механики работают на исполняемых сценариях, а не только отображаются.
- Автотесты проходят, ошибка генератора не маскируется подбором нескольких ручных примеров.
- Перечислить устройства/браузеры, разрешения viewport и результаты **фактически проведённых** замеров FPS, памяти и времени генерации. Запрещено заявлять «60 FPS везде» без тестов.
- Каждый неудовлетворённый пункт матрицы указывается как `FAILED/BLOCKED/NOT TESTED` с точной причиной. Отметка `PASS` допустима только при наличии доказательства.

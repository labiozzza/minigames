# MiniGames — AssetGen: ТЗ на субагента и конвейер игровых ассетов

**Версия:** 1.0 · **Статус:** обязательное дополнение к `01_TECHNICAL_SPEC_PLUMBER.md` и `02_OPENCODE_EXECUTION_RULES.md`.

## 1. Роль и границы

Создать переиспользуемый для всей платформы MiniGames конвейер **AssetGen**: OpenCode формирует структурированные заявки на игровые спрайты, агент генерирует изображения через доступный GPT Image API, проверяет кандидатов, исправляет/повторяет генерацию, готовит Phaser-совместимые файлы, регистрирует результаты и возвращает явные статусы. Обязательна работа при отсутствии доступа к генерации: вместо блокировки остальной разработки агент автоматически готовит **явно помеченные временные примитивные заглушки**.

**Три строго разных статуса:**
- `APPROVED`: финальный ассет, прошедший техническую и визуально-семантическую проверки, интеграцию на реальной сцене; разрешён в релизе.
- `PLACEHOLDER`: временная техническая примитивная графика для разработки и тестирования, никогда не финальный ассет.
- `BLOCKED` / `WAITING_*`: ассет отсутствует, требуется доступ к провайдеру / лимит / ручная проверка; остальные независимые задачи выполняются.

Скилл OpenCode — инструкция, а не автоматически доступная функция Image Gen. Запросы к GPT Image исполняются **только через реально доступный инструмент/API с отдельными действительными разрешениями и квотами**. Наличие подписки ChatGPT не гарантирует API-доступа и не даёт права утверждать, что OpenCode может вызвать генератор ChatGPT. Прототип реализации включает адаптер OpenAI Images API при `OPENAI_API_KEY`, без вшивания секретов. Предусмотреть возможность замены адаптера; не придумывать несуществующие инструменты.

## 2. Где лежит и как вызывается

```
.opencode/agents/assetgen.md
.opencode/skills/minigames-assetgen/SKILL.md
.opencode/skills/minigames-assetgen/scripts/assetgen.py
.opencode/skills/minigames-assetgen/examples/pipe_straight.request.json
```

OpenCode (основной агент) может делегировать `@assetgen` запрос на производство, проверки и подготовку конкретной партии. Субагент читает skill и пользуется CLI. Агента можно также вызвать вручную. Размещать только в существующем проекте после проверки конфликтов имён, не перезаписывать глобальные настройки OpenCode и чужие навыки.

## 3. Заявка и стилистический контракт

Минимальная схема `AssetRequest`: `asset_id`, `game_id`, `category`, `kind`, `prompt`, `style_id`, `style_reference_files[]`, `logical_cell_px`, `port_mask`, `output`, `animation`, `target_roles[]`, `acceptance`. Критические поля валидируются до внешнего вызова. Для каждой игры поддерживается согласованный `StyleBible`: ракурс (единая изометрия/фронтальная 2.5D без произвольного изменения), свет, толщина материалов, прозрачность, контур, палитра, reference assets (2–5 утверждённых), ограничения на тени и геометрию. Эталон утверждается человеком или явно указанным независимым проверяющим; нельзя считать 2–5 случайных результатов автоматическими референсами.

Трубы генерировать предпочтительно **по одному ассету / состоянию в одном запросе**. Не полагаться на то, что Image Gen нарисует точно совпадающие каналы и точки соединения для Phaser: **логические порты, hitbox, маски жидкости, pivot и соединительные контуры задаются детерминированной геометрией, не извлекаются из произвольного изображения наугад**. Для поворотов использовать трансформации спрайта; проверить ориентации 0/90/180/270. Для частично заполненных/полных/пустых труб использовать один визуальный базис и процедурный водяной слой; если нужно — отдельные слои `back`, `liquid-mask`, `front`, `highlights` с проверенной сборкой. GPT-спрайт — художественный слой, а не источник игровой физики.

## 4. Конвейер обработки

`REQUESTED → GENERATING → GENERATED_RAW → VALIDATING_TECH → VALIDATING_VISUAL → PROCESSING → READY_FOR_INTEGRATION → APPROVED`.

При непрохождении: `RETRY_REQUIRED → GENERATING` (максимум 3 попытки при доступном провайдере), после лимита: `WAITING_FOR_LIMITS`, после отсутствия ключа/доступа: `WAITING_FOR_PROVIDER`, после неверных параметров: `BLOCKED_CONFIG`, после 3 плохих результатов: `MANUAL_REVIEW_REQUIRED`. Во всех случаях, если работа требует изображения, создать `PLACEHOLDER` в отдельной папке, а финальную заявку **оставить открытой**.

Файлы заявки, версии промпта, ошибки (без ключей), попытки, `next_retry_at`, согласие на дополнительные затраты, отчёты валидаторов и SHA-256 исходников/результатов сохраняются на диске; очередь переживает перезапуск процесса. Проверка `next_retry_at` происходит только когда агент/worker **реально запущен** — скилл не умеет сам работать в фоне без внешнего планировщика. OpenCode не должен обещать самостоятельное возобновление по времени, если фонового запуска не настроено.

## 5. Проверки качества (обязательные)

**A. Формат:** реальное PNG с RGBA, декодируемость, размер в пределах, отсутствие пустого/повреждённого файла, корректный цветовой профиль, SHA-256. Файл может быть приведён к единому формату в рабочей копии без изменения оригинала.

**B. Прозрачность:** внешние углы и зоны вне объекта — alpha=0 (или разрешённая небольшая доля edge anti-alias), ненулевые прозрачные области (не псевдошахматный фон), bounding box видимой части, отступ от границы **кроме сторон с активными портами**, отсутствие обрезанных краёв; проверить на светлом, тёмном и шахматном превью. Наличие канала alpha **само по себе недостаточно**. Прозрачная стеклянная часть трубы может иметь частичный alpha внутри объекта — нельзя ошибочно вырезать стекло.

**C. Геометрия:** размеры и позиционирование, pivot, сопоставление видимых патрубков с формальным `port_mask`, отсутствие выступов за границы клетки/стыков, читаемость в масштабе 64–96 px, отсутствие орнамента, перекрывающего внутреннюю маску воды. Поскольку пиксельные проверки не доказывают правильность стыков, необходим эталонный overlay-тест в сетке с вращениями.

**D. Стиль и семантика:** проверять образец рядом с 2–5 утверждёнными референсами с помощью доступного vision-модуля либо явной человеческой проверки: ракурс, освещение, материал, детализация, блики, палитра, толщина корпуса, геометрический тип трубы, количество отверстий, отсутствие текста/лишних объектов. Метрики RGB/гистограммы **не являются доказательством стилистического сходства**. Если vision недоступен, выдать `MANUAL_REVIEW_REQUIRED`, а не `APPROVED`.

**E. Интеграция:** визуальные кадры реальной Phaser-сцены в нескольких разрешениях, повороты, анимация воды по маске, открытие клапанов, победа, прозрачность и тени. Без фактического теста нельзя утверждать `APPROVED`.

Каждая причина отказа фиксируется кодом и кратким подробным объяснением для следующего промпта. Не повторять идентичный запрос без изменения диагностированной проблемы.

## 6. Нарезка, слои и выходные файлы

Использовать приоритет: `один PNG на кадр/состояние` → геометрически нормализованные отдельные файлы → texture atlas (`PNG + JSON` Phaser-friendly). Для готовых сеточных спрайт-листов **только явная** сетка `rows/cols/frameWidth/frameHeight`, а не автоматическая догадка по неравномерной картинке. Если нарезка из Image Gen приводит к обрезанию/изменению масштаба кадров, отклонить и заказать независимые кадры или ручной контроль.

Выход каждого финального ассета: `source/raw`, `processed/png`, `atlas/png + atlas/json` (когда нужен), `geometry/mask`, `metadata.json`, `validation-report.json`, превью на 3 фонах. Метаданные включают `asset_id`, `state`, `version`, `style_id`, `origin`, `ports`, `mask_ref`, `source_sha256`, `license/provenance`, `is_placeholder`, `review_status`.

## 7. Примитивные заглушки при отсутствии изображений

**Обязательное требование, а не опция.** Если генерация невозможна, лимит закончился, нет ключа, ассет не прошёл проверку или ожидание затянулось, AssetGen создаёт простой **технический** визуальный заменитель с правильной игровой геометрией:

- прямая труба — вертикальная/горизонтальная полоса с читаемой внутренней полостью;
- угловая — L-контур;
- Т-/крест — контуры с 3/4 ветвями;
- клапаны/фильтры/смесители — символ на основном контуре;
- источник/приёмник — различимые круг/контейнер с стрелкой/цветом и, при необходимости, числом порций;
- окружение — простой геометрический силуэт.

Заглушки создаются **программно, локально, без Image Gen**, с прозрачным PNG или через Phaser Graphics, соответствуют `logical_cell_px`, `ports`, pivot, hitbox и маске воды. Содержат **явную маркировку `PLACEHOLDER`** в manifest, а в dev-сборке — заметный бейдж/водяной знак, чтобы их невозможно было случайно принять за финал. Хранятся отдельно от финальных ассетов; loader умеет выбирать fallback, не меняя ID логических ресурсов. Заглушки могут использоваться в unit, E2E, генераторе, UI и отладке, но **не могут** закрывать визуальную приёмку этапа 2 или финальный релиз.

Повторные запуски конвейера **не перезаписывают** финальные ассеты заглушками, не удаляют старые результаты и не теряют заявки. При готовности ассета выполняются replace → atlas rebuild → проверка подключения → visual regression → изменение статуса; физика игры не меняется.

## 8. Квоты, сбои и оплата

Возможные сбои: `429 rate_limit_exceeded`, `insufficient_quota`, отсутствие API-ключа/прав, `401/403`, сетевые ошибки, недоступная модель или неподдерживаемая прозрачность. Не считать это сбоем игровой разработки. Для временных 429 соблюдать `Retry-After`, если передан; иначе ограниченная экспоненциальная задержка и `next_retry_at`. **Недостаточный баланс или отсутствие доступа не устраняются ожиданием**: `WAITING_FOR_PROVIDER` до реальной настройки доступа/оплаты. Не запускать бесконечные циклы или быстрые повторные вызовы. Не использовать неофициальные способы обхода ограничений. Не выводить `OPENAI_API_KEY` в логи. Зафиксировать бюджет запросов и лимит попыток; затратные вызовы допустимы только после разрешённой настройки ключа/бюджета.

**Квоты ChatGPT и OpenAI API — отдельные механизмы.** Подписка ChatGPT не предоставляет OpenCode автоматический API-доступ. Конкретный GPT Image model выбирается из реально доступных моделей, проверяется поддержка `background=transparent`, `output_format=png` и актуальная цена/лимит. Модель не прибивать к устаревающему названию.

**Когда провайдер недоступен, OpenCode обязан работать дальше:** ядро симуляции, решатель, генератор, UI на заглушках, обучение, звук, backend, офлайн/сохранения, конфигурация, тесты. В матрице требований указывать функциональные проверки `PASS`, но графические `BLOCKED_ASSET`. Нельзя смешивать эти статусы в одну надпись «этап завершён». Автоматические попытки возобновления только когда есть работающее расписание/worker и соблюдены лимиты.

## 9. Модульность и безопасность

- AssetGen — инструмент сборки/разработки, **не обязательная серверная зависимость** клиента PWA. Пользовательская игра не должна вызывать платный Image API.
- Нет автоматического изменения production VPS, secrets, shared SDK, «Переливашек» и графических ресурсов других игр.
- Сгенерированные изображения не исполняются как код. Импортируемые изображения декодировать в ограниченном процессе/с проверкой размеров.
- Любая автоматическая публикация в prod требует действующей процедуры review/релиза.
- Распознавание стилистического сходства — вероятностная проверка, требует проверяемого отчёта; не заявлять 100% гарантии.

## 10. Приёмочные сценарии AssetGen

1. Правильный прозрачный 256×256 PNG → `VALID_TECH`; видны оба конца трубы; создано превью на трёх фонах.
2. RGB-картинка с белым фоном → отклонена, не маркируется прозрачной.
3. PNG с alpha=255 во всех точках → отклонён независимо от наличия RGBA.
4. Труба обрезана по краю → отклонена по safe padding.
5. Файл с корректной прозрачностью, но неверной формой/ракурсом → не одобряется без vision/ручного review.
6. При отсутствии API key → `WAITING_FOR_PROVIDER` + создана `PLACEHOLDER` для всех недоступных запрошенных сущностей, остальные задачи продолжаются.
7. При HTTP 429 → `WAITING_FOR_LIMITS`, записано время повторной попытки, нет частых платных повторов; PNG заглушка работает.
8. После возобновления провайдера: готовый PNG, alpha-check, визуальная проверка, нормализация, маски, atlas, integration screenshot; только затем `APPROVED`.
9. Для атласа все frame rect лежат в пределах текстуры, размеры совпадают с реальными файлами; ни один спрайт не обрезан.
10. Обновление спрайта не меняет логические `ports`, не ломает «Переливашки» и не теряет сохранённые уровни.
11. При невозможности интеграционного/визуального теста — `READY_FOR_INTEGRATION` / `MANUAL_REVIEW_REQUIRED`, но не `APPROVED`.
12. Отчёт включает `ready`, `placeholder`, `waiting`, `rejected`, `blocked`, список зависимых задач и инструкции дальнейшей работы.

## 11. Минимальный объём первой партии

`pipe_straight`, `pipe_elbow`, `pipe_t`, `pipe_cross`, `pipe_cap`, `valve_basic`, `source_basic`, `receiver_basic`. Затем смесители, разделённые каналы, переключатели, декорации и 12–16 коллекционных предметов. Геометрические маски и атласы должны соответствовать игровому ядру, утверждённые художественные слои не должны нарушать логические порты.

## 12. Требования к реализации скилла в этом пакете

Поставляются инструкция `SKILL.md`, субагент `assetgen.md` и **стартовый CLI**, поддерживающий: создание заявок, хранение статуса на диске, программные заглушки, проверки PNG, нормализацию, нарезку и упаковку в атлас; при доступном API и явном разрешении затрат — вызов GPT Image API и независимый vision-review по референсам. Требуется довести конвейер до production-уровня: автоматизировать полный integration gate, подтверждённый review, оркестрацию очереди/переиспользование готовых результатов, регрессию и отчёты. Локальный CLI сам **не объявляет финальное APPROVED**, даже при успешной проверке зрения. Наличие файла `SKILL.md` **не равно** настроенному Image API, работающему агенту и автоматической приёмке готовой графики.

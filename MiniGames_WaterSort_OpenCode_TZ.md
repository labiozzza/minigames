## 1. Продукт и границы задачи

Создать **новый проект с нуля**, временное название платформы `MiniGames`. Первая игра — **«Переливашки»** (рус.) / **Water Sort** (англ.), классическая сортировка жидкостей по пробиркам. Платформа содержит адаптивный каталог карточек игр, блок «Продолжить», настройки, PWA-установку, offline-режим, импорт/экспорт сохранений. В первом релизе доступна одна полноценная игра. Архитектура позволяет регистрировать следующие игры отдельными модулями.

Целевая модель: полностью бесплатное приложение **без рекламы, монетизации, регистрации, аккаунтов, аналитических трекеров и серверного API**. Полноценная работа после первоначальной загрузки без интернета. Деплой как набора статических файлов на VPS или статический хостинг.

Обязательно реализовать **весь** описанный функционал первого релиза. Новые игры, аккаунты, облачную синхронизацию, рекламу, редактор уровней и CI/CD развёртывания **не создавать**.

## 4. Базовые правила Water Sort

- Каждый сосуд вмещает **ровно 4 единицы** жидкости. Начальный состав уровня: от **3 до 12 разных цветов**, по **ровно 4 единицы каждого**, как правило **две пустые пробирки**. Диапазон: от 5 до 14 сосудов.
- Стартовый уровень — смесь цветов в заполненных пробирках; пустые служат буферами. На уровне 3 цветов обычно 3 заполненных + 2 пустых; на уровне 12 — 12 заполненных + 2 пустых. Не генерировать больше жидких единиц, чем позволяет ёмкость.
- Управление **двумя нажатиями**: первое на источнике выбирает и приподнимает его, второе на приёмнике пытается перелить; повторный выбор исходной пробирки снимает выделение без ошибки.
- Источник должен содержать жидкость. Приёмник должен иметь свободное место и быть либо пустым, либо иметь на верхнем слое **тот же реальный цвет**, что у источника. Переливать поверх другого цвета нельзя.
- Одним ходом автоматически переносить `min(число подряд одинаковых верхних слоёв источника, свободная вместимость приёмника)` единиц. Если на приёмнике хватает места только для части группы, перенести эту часть.
- Запрещены переполнение, переливание из пустого, в полный, к себе, переливание разных цветов и параллельные ходы.
- Неправильная попытка: лёгкое покачивание источника и короткий тихий синтезированный звук; никаких модальных ошибок. Повторное нажатие на источник — обычная отмена выбора.
- Полностью собранная пробирка (4 единицы одного цвета) получает мягкое однократное свечение, **но НЕ блокируется**. При разрушении собранной комбинации отметка исчезает. Отдельная собранная пробирка не равна победе.
- Победа: **все непустые пробирки заполнены до 4 единиц и одноцветны**, остальные пустые. Показать анимацию, затем окно победы с номером уровня и кнопкой «Следующий уровень». Не переключать автоматически.
- Нет лимитов времени, ходов, счётчика ходов, звёзд и состояния проигрыша. Пропуска уровней нет. Не выводить автоматические уведомления «тупик».
- Активные действия игрока заблокированы на время анимации одного переливания. Модель должна применять действие атомарно: не оставлять частично изменённое состояние при прерывании, скрытии страницы, закрытии игры или WebGL context loss. В мгновенном режиме то же правило, но анимация почти отсутствует.

Пример доменных типов (уточнять по необходимости):

```ts
type ColorId = string;
type LayerId = string;
type TubeId = string;
interface Layer { id: LayerId; color: ColorId; }
interface Tube { id: TubeId; layers: Layer[]; }
interface Move { sourceTubeId: TubeId; targetTubeId: TubeId; layerIds: LayerId[]; }
interface PuzzleState {
  levelId: string;
  tubes: Tube[];
  knownLayerIds: LayerId[];
  moveHistory: Move[];
}
```

Поле `color` — **истинный цвет**, доступный только доменной модели, solver-валидатору и renderer для уже раскрытого слоя. Для подсказок создавать **отдельное информационно ограниченное представление**, где неизвестные слои представлены `unknown`, а не передавать `PuzzleState` целиком.

## 5. Скрытые слои: Mystery Layers

**Ввод:** после 100 обычных уровней, начиная с **уровня 101**. К уровню 300 максимально допустимая доля скрытых слоёв достигает **50%** от всех жидких единиц; не обязательно ровно 50% на каждом уровне. В рамках волнообразной сложности более простые уровни могут иметь меньше скрытых слоёв.

- Скрытый слой — обычный слой одного из существующих цветов, изображаемый **одинаково** для всех истинных цветов: тёмный блок со знаком `?`. Никакие оттенки, узоры, размеры, частоты мерцания, положения и другие признаки не должны кодировать реальный цвет.
- В стартовом состоянии **верхний слой каждой непустой пробирки видимый**. Остальные скрытые слои распределяются **контролируемо-случайно**, с проверкой корректности конфигурации.
- Слой раскрывается, когда становится доступен взгляду игрока (верхним слоем после переливания); в этот момент анимированно заменять тёмный блок на настоящий цвет. После раскрытия **слой остаётся известным навсегда в рамках текущего прохождения**, даже если снова оказывается под другим слоем или перемещён в другую пробирку.
- **Отмена хода** возвращает расположение жидкостей, но НЕ отменяет новые знания. **Перезапуск** восстанавливает исходную расстановку, очищает историю ходов, но сохраняет знания о раскрытых слоях. **Повторное прохождение уже завершённого уровня из сетки** начинается с исходной расстановки и очищает раскрытые знания для этого нового захода.
- Идентичность знания привязана к **устойчивому `layerId`**, а не к позиции в пробирке: слой может перемещаться. Информация о слоях сохраняется локально, экспортируется и импортируется вместе с прогрессом.
- При выборе источника верхний цвет должен быть известен игроку: после удаления любого верхнего слоя новый верхний, если ранее скрытый, раскрывается сразу по факту открытия. Техническая модель знает все цвета, поэтому обычные физические правила переливания сохраняются, но интерфейс не должен утекать дополнительную информацию.
- Генератор проверяет, что базовая головоломка действительно решаема со всеми истинными цветами. **Это не обещание, что игрок способен решить её без экспериментов**: разведка и обратимые ходы входят в дизайн.
- Отмена не ограничена; последовательное изучение неизвестных цветов с откатом допустимо намеренно, это **не эксплойт**.
- На уровне 101 — одноразовое **интерактивное обучение**: объяснить `?`, предложить открыть слой, разъяснить сохранение знания после отмены. Можно пропустить; повторно открыть правила через настройки.

## 6. Честные подсказки без «рентгена»

В обычных уровнях — подсветка **двух пробирок** (источник/назначение) для хода, ведущего к решению. Подсказка сама **не выполняет ход** и не ограничена по числу вызовов.

При наличии скрытых слоёв разделить алгоритмы:

1. **Полный генератор/валидатор** знает истинные цвета и использует их **только** для подготовки и сертификации головоломки.
2. **Hint Engine** принимает **только публичную проекцию**: известные цвета/слои, `unknown` для неизвестных, геометрию и публичную историю ходов/раскрытий. Не передавать в этот модуль полный объект со скрытыми цветами и не делать обходные обращения к `seed`, генератору или валидатору в ходе принятия решения.
3. Если по публичным данным можно обосновать гарантированный полезный ход, подсветить его и пометить типом **«Подсказка»**. Гарантированным называть только доказанный по доступной информации ход, а не ход из решения, которое использовало скрытые значения.
4. Если гарантии нет, предложить **«Разведку»**: допустимый ход для открытия неизвестного слоя. Не обещать, что он ведёт к решению; выбрать разумную эвристику (сколько знаний может открыть, сколько свободных буферных мест сохраняется). Если публично известный полезный ход отсутствует, предложить отмену/перезапуск **без утверждения, что уровня решить нельзя**.
5. На разных возможных истинных раскладках со **строго одинаковым публичным состоянием** и одинаковой публичной историей Hint Engine должен выдавать идентичную подсказку. Эта non-interference-гарантия обязательна в unit-тестах. Скрытый `seed` никогда не участвует в принятии решения Hint Engine.
6. Подсказка не запускает необратимое действие, не раскрывает `?` сама по себе и не ломает анимацию.

Для классических уровней и полностью раскрытого состояния использовать solver для нахождения пути к победе, но предусмотреть ограничение вычислительного бюджета. Не выдавать эвристику за доказанный оптимальный ход. Если поиск не завершился — корректная неопределённость, retry/разведка/отмена вместо ложной «гарантии».

## 7. Бесконечная детерминированная генерация, баланс и сертификаты решения

**Одинаковый номер уровня у всех пользователей означает одну и ту же головоломку.** Поддерживать возвращение к пройденным уровням; они должны воспроизводиться по номеру/версии алгоритма, стабильному seed и конфигурации.

- Уровни **1–100**: постепенный рост с 3 до 12 цветов, без скрытых. С уровня **101** вводить скрытые цвета; до **300** плавно повышать допустимую скрытность до 50%; затем циклы/волны сложности с периодическими облегчениями.
- Начальная кривая хранится в `config`, а не в коде `if` на каждом экране. Конфигурация включает диапазоны цветов, глубину перемешивания, число пустых пробирок (обычно 2), ориентиры сложности, диапазоны скрытых слоёв, волновой профиль, бюджеты генерации и проверки.
- Применить версионированный PRNG с фиксированным алгоритмом и явно нормализованными входами: `(gameId, levelNumber, generatorVersion, balanceVersion)`. Запретить `Math.random()` при вычислении содержимого уровней. Поведение не зависит от устройства, скорости CPU, локали или текущего времени.
- Сильная рекомендация: **конструктивный генератор, создающий головоломку вместе с проверяемым путём решения**, например генерировать допустимые предшествующие состояния от решённого состояния, проверяя возможность каждого обратного перехода по правилам прямой игры. Важно, чтобы конечная стартовая конфигурация удовлетворяла требованию полных цветных пробирок плюс двух пустых. Любые кандидаты после конструктивного построения обязательно проверять независимым `applyMove` на действительном пути решения от начала к цели.
- Сертификат решения — последовательность **легальных ходов**, воспроизводящая выигрыш. Тест валидации сертификата доказывает **существование** решения и не обязан доказывать его минимальность. Если задана метрика «минимальное количество ходов», она может быть указана только после действительно исчерпывающего/доказательного вычисления; иначе это длина найденного пути или оценка.
- Сложность нельзя мерить одним количеством цветов: учитывать найденную длину решения, доступность буферов, чередование цветов, скрытность, потенциальные развилки. Не выдавать эвристическую оценку за точную математическую сложность.
- Генерация, проверка, подготовка подсказок идут **в Web Worker**, не блокируют UI. Workers должны поддерживать отмену ненужного запроса, очередь и ограничения по ресурсам.
- **Критически важно:** время поиска и количество неудачных попыток не должно менять результат уровня. При исчерпании бюджета нельзя брать «первую найденную случайную подходящую головоломку»: это сломает идентичность уровней на разных устройствах. Решение: фиксированная последовательность кандидатов с детерминированным правилом выбора и ограничениями, не зависящими от wall-clock; статический версионированный проверенный fallback/каталог кандидатов, индексируемый номером. Фоновое вычисление может продолжаться дольше, но результат не должен ветвиться по времени.
- Проводить **предварительную генерацию и проверку первых уровней**, в том числе обучения. В игре заблаговременно готовить последующие уровни и кешировать готовые конфигурации с контрольной суммой/версией. Базовые начальные уровни работают мгновенно даже офлайн.
- Сохранить replay/seed и версии для каждого начатого уровня. При нехватке кеша детерминированно восстановить его из неизменяемой версии генератора.
- **Политика неизменности выпущенных уровней:** однажды опубликованная бесконечная последовательность `levelNumber -> puzzle` не меняется при обновлении. Обычное изменение конфигурации баланса в следующих релизах не должно молча переназначать уровень №500. Исправления баланса для уже существующей последовательности выполняются только без изменения её идентичности, либо через **явно новую последовательность/режим с отдельным namespace и нумерацией**. Архивные генераторы и их конфигурации сохраняются для старых сохранений. Это обязательное архитектурное следствие одновременно «одинаковых уровней для всех», бесконечного локального генератора и offline-режима: нельзя узнать, какие бесконечные номера уже кем-то открыты.
- Для массовой проверки и реального игрового режима предусмотреть **детерминированную безопасную деградацию**: если продвинутый solver не может эффективно проверить кандидат на высокой сложности, не зависать и не публиковать неподтверждённый пазл; выбирать заранее проверенный неизменяемый fallback. При невозможности построить/получить уровень честно показать техническую ошибку с повтором, не имитировать успех.

## 8. История, навигация, уровень и сохранение

- **Неограниченная отмена** всех ходов до старта текущей головоломки. Историю хранить компактно как последовательность действий / обратимых операций, не обязательно полные слепки. Разведанные цвета при отмене не скрываются.
- **Перезапуск**: если были ходы, запросить подтверждение. Сбросить расположение к исходному и очистить историю, сохранив открытые цвета. При нуле ходов перезапуск без дополнительного подтверждения.
- **Только один активный незавершённый уровень** на всю игру. Если игрок переходит на другой уровень и текущий изменялся, предупредить, что незавершённое состояние будет потеряно. Если ходов нет — переход без подтверждения. Вернуться в каталог/закрыть PWA — **НЕ значит переключить уровень**, незавершённый уровень сохранить.
- **Сетка уровней**: адаптивная сетка с номерами, состояниями «пройден», «текущий», «заблокирован». Пройденные уровни повторно доступны, будущие — нет. Для тысяч уровней сделать страницы/ленивую визуализацию. **Без отдельного поля быстрого перехода по номеру** для обычного игрока; оно есть только в dev-панели.
- Запуск повтора пройденного уровня начинает новую сессию с очищенной разведкой скрытых цветов. Общий максимальный достигнутый уровень **не сбрасывается**. Действия в повторе не открывают новые будущие уровни.
- Хранить: id игры, максимальный открытый/достигнутый уровень, перечень пройденных, активный `levelId`, seed и версии, исходную конфигурацию или ссылку на неё, текущие пробирки, id известных слоёв, историю ходов, флаги обучения, настройки. Также сохранять последнюю игру для кнопки «Продолжить».
- Автосохранение **после каждого завершённого логического действия**, при уходе в каталог и `visibilitychange`; данные не должны оставаться только в RAM. Во время анимации сохранить однозначное логическое состояние, на котором безопасно восстановиться.
- Первичный принцип — **локальное хранение**. Для компактных метаданных можно `localStorage`; для неограниченной растущей истории/объёмных сохранений предпочтительнее `IndexedDB` через изолированный адаптер, поскольку у `localStorage` ограниченная квота. Это не сервер и не нарушает offline-требование. **Нельзя молча обрезать историю отмен.** При нехватке места обработать ошибку, предложить экспорт, не разрушать существующие сохранения.
- `schemaVersion` для сохранений, миграции при обновлении, проверка структуры и восстановление/бэкап при неудачной миграции. Согласованная модель хранения допускает будущий облачный адаптер, но сетевой адаптер сейчас не реализовывать.

### Экспорт и импорт

В настройках платформы кнопки «Сохранить прогресс» (экспорт всех игр в JSON) и «Восстановить прогресс» (выбрать JSON-файл). Работает офлайн. Включить `formatVersion`, версии сохранений, `games`, `settings`, метаданные и контроль целостности для обнаружения случайной порчи. Контрольная сумма **не криптографическая гарантия подлинности**. Не принимать произвольный исполняемый код, URL, прототипные ключи и не доверять импортируемым данным.

Если на устройстве уже есть прогресс, предоставить **выбор: заменить / объединить / отменить**, с предварительным сравнением. При объединении: сохранить объединение множеств пройденных уровней и максимальный прогресс только при совместимых `gameId` и версиях уровня. Конфликтующие состояния одного незавершённого уровня **не смешивать покомпонентно**: выбрать одну целостную сессию, показав выбор пользователю. При импорте на конфликтующие версии генератора — сохранить старую совместимую конфигурацию или предложить отмену, а не подменять содержимое пазла.

До модификации создавать резервную копию актуальных данных (в рамках доступного места; при риске квоты сначала предложить скачать текущий экспорт). Импорт сначала полностью разобрать и проверить, затем применить транзакционно насколько позволяет хранилище; при ошибке откатить.

## 9. Интерфейс, стиль и визуальные эффекты

**Визуальный стиль** — современный минимализм: стеклянные прозрачные пробирки, яркие различимые жидкости, аккуратные блики, мягкие тени, немного свободного пространства. Процедурная графика средствами Phaser; не требуются скачиваемые спрайт-листы. Не подключать тяжёлую физику жидкостей.

**Игровой экран:** сверху кнопка «Назад в каталог», номер уровня и настройки; в центре поле пробирок; внизу три большие сенсорные кнопки: отмена, перезапуск, подсказка. Кнопки HTML/CSS. Счётчик ходов и таймер не выводить. Поле адаптировать к портретной и альбомной ориентации, небольшим смартфонам, планшетам и десктопу. До 14 пробирок — размещение в несколько рядов без обрезания; если не помещаются, использовать прокручиваемую область / обоснованный zoom при сохранении пригодных touch-целей (ориентир не меньше 44×44 CSS px для интерактивных элементов).

**Анимация переливания:** поднять выбранный сосуд, переместить к приёмнику, наклонить, сформировать струю цвета верхней жидкости, согласованно уменьшать/увеличивать уровни, слегка колебать поверхность, вернуть сосуд. Анимация состояния полностью отделена от расчёта хода. Запретить столкновения, двойное исполнение, некорректное направление струи и визуальные переливы за края. Сложность графики адаптировать к устройству.

Настройки скорости: **обычная / быстрая / мгновенная**, сохраняются. Уважать `prefers-reduced-motion` (по возможности уменьшать анимации и интенсивность эффектов независимо от игрового хода).

Пробирка, собранная в четыре одинаковых слоя, получает мягкое свечение без блокировки. Скрытые слои — тёмные со знаком вопроса и плавным раскрытием. Подсветка источника/цели для подсказок различима в обеих темах.

**Цветовая тема:** светлая и тёмная. Начальная — по системной теме, ручной выбор в настройках с приоритетом над системой и локальным сохранением. Тема едина для всей платформы и игры. Палитра включает 12 устойчивых `ColorId`, различимых по возможности на обеих темах. Опция «Показывать символы цветов» **выключена по умолчанию**: при включении каждый цвет имеет уникальный постоянный знак во всех уровнях. У скрытых слоёв знак цвета отсутствует до раскрытия, виден только `?`.

**Локализация:** русский по умолчанию и английский с **ручным переключателем**. Все сообщения, обучение, экран победы, каталог и настройки через словари `ru`/`en`. Не внедрять обязательное автоопределение языка. Переключение работает offline, выбор сохраняется.

**Каталог:** адаптивная сетка карточек (иконка/обложка, название, короткое описание). На старте одна активная игра. Вверху блок «Продолжить» для последней игры, если она запускалась. Не добавлять фальшивые «доступные» игры. Иконки и обложки платформы/игр — **единая минималистичная дизайн-система**, SVG с мягкими градиентами, простыми формами, с производными PNG для PWA (`192x192`, `512x512`, maskable; дополнительные размеры при необходимости). Имя платформы конфигурируемое `MiniGames`.

**Интерактивное обучение:** при первом запуске обычных уровней объяснить два нажатия, правило совпадающих цветов, цель сортировки. Интерактивное, краткое, с подсветкой и действием игрока; один раз, можно пропустить, повторно открыть из настроек. Второе обучение скрытым цветам на уровне 101 (см. §5).

## 10. Звук, музыка и вибрация

**Все звуки синтезировать Web Audio API**, без внешних аудиофайлов: звук выбора, движения/переливания, недопустимого действия, открытия скрытого слоя, собранной пробирки, победы, UI-нажатий. **Фоновая музыка** — спокойный эмбиент с тихими синтезированными тембрами, медленными гармониями и музыкальными вариациями; без навязчивых коротких циклов. Процедурная композиция не должна создавать заметную CPU-нагрузку, утечку AudioNodes, щелчки на стыках или незавершённые ноты.

В настройках независимые переключатели и уровни громкости для **музыки** и **эффектов**, отдельный переключатель вибрации. `navigator.vibrate` использовать только если реально поддерживается; его отсутствие нормально (в частности на части устройств iOS). Учесть политику браузеров: создавать/возобновлять AudioContext после пользовательского взаимодействия. При скрытии вкладки, выходе в каталог и отключении музыки — корректно приостанавливать/затухать звук. При повторном запуске не должно быть двойной фоновой музыки. AudioContext закрывать/освобождать при полном выходе из игры, если он принадлежит игре.

## 11. PWA, кеш и обновления

- Web App Manifest с корректными `name`, `short_name`, `icons`, `display: standalone`, цветами, scope/start_url и поддержкой установки там, где браузер позволяет.
- При первом запуске подготавливать **оболочку платформы и весь минимум для офлайн-запуска Water Sort**. Остальные будущие игры — динамическая загрузка и явная кнопка «Скачать для офлайн» на карточке. Показывать реальное состояние загрузки/ошибки/готовности; отметка «Офлайн доступно» только после успешного кеширования всех зависимостей игры. Содержание проверять на уровне манифеста версий/списка ресурсов; не утверждать, что весь кеш криптографически проверен без реализованных хешей.
- Правильно кешировать динамические JS chunks, SVG, иконки, шрифты (если нужны), конфигурации и заранее сгенерированные уровни. Не требовать интернет для уже загруженной игры, генерации новых уровней, подсказок, настроек, импорта/экспорта.
- В каталоге после **первого завершённого уровня** однократно/ненавязчиво предложить установить PWA. В настройках доступен пункт «Установить приложение». В браузерах без события прямой установки показывать инструкции, а не неработающую кнопку. После отказа не спамить повторными баннерами; установленному приложению предложение не показывать.
- Обновление **по запросу**: Service Worker скачивает новую сборку по стандартной схеме, показывает «Доступна новая версия» и кнопку «Обновить»; никакой принудительной перезагрузки посреди уровня. По согласию — дождаться/обеспечить успешную запись актуального состояния, активировать обновление и перезагрузить интерфейс. После reload мигрировать и восстановить сохранение. Откат и ошибки кеша — с понятным UI.
- `HTTPS` обязателен на опубликованном домене (localhost допустим для разработки). Поддержать правильный `base`/роутинг для корня домена и подпути; провести реальный offline-тест **production-сборки**, не только `vite dev`.
- Игра должна корректно возобновляться после обычных reload, `Back/Forward` и запуска установленной PWA, насколько позволяет браузер; не допускать потери активного хода.

## 12. Браузеры, доступность и производительность

Поддерживаемые цели: современные Chrome, Edge, Firefox, Safari, Яндекс Браузер, Samsung Internet на Android, iOS/iPadOS, Windows, macOS, Linux. Приоритет — современные мобильные устройства, включая бюджетные Android. Версии и реально проверенные браузеры указать в отчёте. Playwright-эмуляция viewport **не равна тесту реального iPhone**; не заявлять физическое тестирование без устройства.

- Цель — **60 FPS на устройствах, которые способны на это**, с адаптивным уменьшением интенсивности теней, бликов, движения поверхности и других украшений. Не ухудшать игровую логику при просадке FPS. Отсутствие 60 FPS на бюджетном устройстве не должно делать игру непригодной.
- Никаких зависаний главного потока из-за solver/генератора. Внешние ожидания, отмена фоновых запросов, graceful timeout и честные сообщения в dev-панели.
- Корректная обработка resize, safe-area, touch, Pointer Events, масштабирования и контекстной потери WebGL (на поддерживаемом оборудовании). UI на HTML должен быть доступен с клавиатуры, иметь читаемый контраст, названия кнопок/aria-метки и видимый фокус. Игровые действия по pointer/touch; по возможности поддержать выбор/ход клавиатурой.
- При отсутствии вибрации, невозможности воспроизвести Web Audio до жеста или невозможности установить PWA — не ломать игру.

## 13. Режим разработчика (строго DEV only)

Создать диагностическую панель **исключительно для development-сборки**: открыть любой уровень по номеру/seed, отобразить полный истинный состав и скрытые цвета, воспроизвести найденный путь решения, проверить подсказку, переключить открытые/закрытые слои в визуализаторе, показать версию генератора, seed, время генерации, длину найденного решения/сертификата и метрики поиска. Можно воспроизводить проблемные кейсы из автоматических тестов.

В production-бандле панель и её код должны быть исключены через compile-time branching / dynamic import, не просто спрятаны CSS. Не менять сохранение пользователя при тестировании без явного предупреждения в dev. Редактор пользовательских уровней **не нужен**.

## 14. Автоматические тесты — обязательные группы

**Unit/domain:**

1. Валидность ходов: пустая/полная пробирка, несовпадение цветов, частичный перенос одинаковой группы, четыре верхних слоя, повторный выбор, победа и её отсутствие в неполном сосуде.
2. Инварианты после каждого хода, отмены, перезапуска: количество слоёв каждого цвета сохраняется (4), общая вместимость не нарушена, слои не дублируются и не теряются.
3. Отмена до начала уровня, история после закрытия приложения, отсутствие потери/удвоения хода при обрыве анимации.
4. Скрытые слои: раскрытие только при достижении верхней позиции, сохранение `knownLayerIds` при отмене/перезапуске, очистка при повторе, привязка знаний к id, а не позиции.
5. Hint Engine: **non-interference** при одинаковом видимом состоянии и разных истинных скрытых цветах, отсутствие чтения полного стейта/seed и ложной маркировки разведки как гарантированной подсказки.
6. Проверка двумерной адаптивной компоновки, темы, локализации, повторных событий, загрузки/уничтожения Phaser.

**Generation/property-based:**

7. Прогнать **не менее 10 000 детерминированных level-id/seed** в автоматическом наборе, включая пороговые номера 1, 2, 3, 99, 100, 101, 102, 299, 300, 301 и высокие номера (например 1 000, 10 000, 100 000). Если тяжёлый solver не укладывается в разумное время, всё равно валидировать конструктивные сертификаты; отдельно запускать обоснованную выборку глубокого полного solver и указывать количество/время. Не подменять отсутствие полного перебора утверждением об оптимальности.
8. Для каждой опубликованной головоломки из набора: соответствие числу цветов и слоёв, допустимость стартовой конфигурации, соответствие cap 50%, обязательный видимый верх, отсутствие одинаковых id, прохождение сертификата решения от начала до финиша с **использованием только правил игрока**.
9. Проверка идентичности: один и тот же `levelNumber` независимо от исполнения, повторного запуска и разных Worker instances создаёт байтово эквивалентный нормализованный puzzle (без времени и нестабильных полей). Снимки фиксированных уровней — regression fixtures на обновления.
10. Проверка, что генерация не зависит от CPU budget, wall-clock, локали и `Math.random`; fallback стабилен и тоже проверен. Тест волнообразной кривой сложности по параметрам, не требующий строгой монотонности.

**Storage and import/export:**

11. Reload на середине уровня, выход в каталог, повторный заход, смена вкладки, сохранение после перезапуска.
12. Импорт при пустом хранилище; replace, merge, cancel; выбор конфликтующей активной сессии; повреждённый JSON; некорректная структура; устаревшая schemaVersion; большой файл; неполный импорт; запасная копия и rollback; недостаток места.
13. Неограниченная история отмен в практическом стресс-тесте большой последовательности; уметь сохранять и загружать её, не обрезая молча.

**Playwright E2E:**

14. Полный пользовательский цикл: каталог → Water Sort → обучение → несколько переливаний → подсказка → отмена → перезапуск → победа → следующий уровень → каталог → «Продолжить».
15. Отдельный тест уровня со скрытыми цветами, включая разведку, раскрытие, отмену и сохранение знания; тест повторного прохождения с чистыми скрытыми слоями.
16. Светлая/тёмная темы, русский/английский, 320px смартфон, типовой современный смартфон, планшет и десктоп; сделать **реальные скриншоты** браузера в `evidence/screenshots/`.
17. **Production PWA offline**: сначала загрузка/кеширование при сети, затем сетевое отключение и полноценная игра, получение следующих уровней, перезагрузка, сохранения, экспорт/импорт; проверка offline readiness.
18. Обновление приложения: проверить prompt-модель и восстановление прогресса на тестовой паре версий, если возможно; документировать способ проверки.
19. Повторные mount/unmount и игра после завершения в течение длительной сессии: отсутствие двойной музыки, висящих listeners и неосвобождённых Phaser objects. При наличии инструментирования — сравнить потребление ресурсов до/после, без необоснованных абсолютных обещаний.

Добавить команды `npm run typecheck`, `npm run lint`, `npm run test`, `npm run test:levels`, `npm run test:e2e`, `npm run build`, `npm run preview` (или документированные эквиваленты). Тесты действительно выполнить. Если автоматический тест зависит от недоступного браузерного окружения, указать это явно и предоставить шаги воспроизведения; не отмечать его как пройденный.

## 15. Итоговые артефакты и приёмка

OpenCode самостоятельно реализует **весь проект целиком**; может разбить работу на внутренние этапы, но **не запрашивает утверждение после каждого этапа**. Если задача объективно не завершена, продолжает исправления в рамках одной работы. Нельзя считать задачу выполненной только из-за зелёных unit-тестов при неработающем UI.

**Обязательные артефакты:**

- Полный исходный код в Git-репозитории, осмысленная структура, `.gitignore`, lockfile, понятные коммиты.
- Реально работающие `npm install`/`npm ci`, `npm run dev`, `npm run build`, `npm run preview`.
- Production сборка `dist/`, которую можно разместить без backend.
- `README.md`: требования Node, команды установки, сборки, тестов, запуск offline.
- `docs/ARCHITECTURE.md`: границы платформы и игровых модулей, жизненный цикл Phaser, модели состояния, звук, кеш, storage.
- `docs/GAME_MODULE_API.md`: пошаговая инструкция добавления второй Phaser-игры, её регистрации в каталоге и включения в offline-кеш.
- `docs/GENERATION.md`: версии и seed, структура сертификата, критерии решаемости, ограничения solver, политика неизменности уровней.
- `docs/DEPLOY.md`: как развернуть dist на статическом сервере/VPS, HTTPS, SPA fallback и заголовки кеширования; примеры Nginx и конфигурации статического хостинга.
- `docs/ACCEPTANCE_REPORT.md`: версия зависимостей, фактически запущенные команды, количество проверенных уровней и ошибок, результаты браузерных/PWA тестов, ограничения, список не пройденных проверок (если есть), честная таблица требований `done/partial/not done`.
- `evidence/screenshots/`: фактические PNG-скриншоты каталога, обычного уровня, уровня со скрытыми цветами, окна победы, светлой/тёмной темы на мобильной/десктопной ширине; `evidence/` с логами/итогами массовой генерации и тестов. Не подменять реальные скриншоты генеративными изображениями.

**Критерии готовности:**

1. Игровые правила полностью совпадают с этим ТЗ; не существует невоспроизводимых уровней или обнаруженных невалидных переливаний.
2. Реально пройдены обычные и скрытые уровни в браузере; пользователю доступна полная игра, не демонстрационная заглушка.
3. Подсказки со скрытыми цветами не используют скрытые значения для выбора ходов; это подтверждено архитектурой и тестами.
4. Сохранение, отмена, перезапуск, переключение, повтор, импорт/экспорт соответствуют согласованной семантике.
5. Каталог, адаптивный UI, темы, два языка, процедурный звук, интерактивные обучения, PWA-кеш, ручное обновление работают.
6. Минимум 10 000 уровня/seed проходят пакетную проверку инвариантов и **проверяемой цепочки решения**; глубокая оптимальность не обещается без отдельного доказательства.
7. Production build запускается и работает автономно после первичной загрузки; новые ресурсы не требуют обращения к CDN.
8. Результаты реального запуска тестов и скриншоты предоставлены; упавшие или пропущенные проверки отражены честно.

**Недопустимые подмены:** фальшивые результаты тестов, `Math.random()` для основной детерминированной генерации, подсказка по секретным цветам, скрытая зависимость от сети, сброс знания при отмене, локальный `dev` вместо проверки `production`, невидимый в production dev-инструментарий вместо его исключения, отключение сложных функций для прохождения тестов.

## Приложение B. Важные уточнения, чтобы не реализовать противоречия

1. **«Неограниченная отмена» vs квота браузерного хранилища.** Не ограничивать функцию искусственно, но честно обрабатывать физическое исчерпание памяти устройства; сохранять компактно, при необходимости IndexedDB.
2. **«Одинаковый уровень №500 у всех» vs возможность изменять баланс.** Нельзя незаметно менять опубликованную бесконечную функцию соответствия уровня головоломке. Для новых правил нужен отдельный версионированный namespace или заранее закреплённые диапазоны до публикации.
3. **«Гарантированно решаемый» vs «можно получить подсказку из текущего положения».** Генератор удостоверяет начальную конфигурацию сертификатом; после произвольных действий игрока поиск может быть сложным/не иметь решения без отмены. Не обещать гарантированную подсказку в невозможных случаях.
4. **«Скрытые цвета не подглядываются» vs полностью локальная игра.** Истинные цвета на устройстве существуют в модели для симуляции, но недоступны алгоритму подсказок через его публичный контракт. Защита от пользователя, специально открывающего DevTools, не является требованием.
5. **«Гарантия решаемости» vs 12 цветов и время проверки.** Приемлем сертификат законного пути решения, а не обязательное доказательство кратчайшего пути. Отсутствие полного перебора не означает, что уровень не проверен на существование решения.
6. **«Широкая совместимость» vs WebGL и PWA-ограничения.** Проверять реальные API; разные устройства неодинаково поддерживают install prompt, вибрацию и звук без пользовательского действия. Недоступные функции корректно деградируют.
